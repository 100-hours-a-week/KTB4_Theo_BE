# SSE 연결 유지 부하 테스트 계획

## 1. 테스트 목적

기존 5초 폴링 테스트에서는 새로운 알림의 발생 여부와 관계없이 사용자 수에 비례해 HTTP 요청과 DB 조회가 반복적으로 증가했다.

이번 테스트에서는 폴링 방식과 구조적으로 다른 SSE 방식이 다수 사용자의 장기 연결을 어느 수준까지 유지할 수 있는지 확인한다.

구체적인 목적은 다음과 같다.

1. SSE 연결을 몇 명까지 안정적으로 수립하고 유지할 수 있는지 확인한다.
2. 사용자 증가에 따라 CPU, JVM Heap, 스레드, GC 사용량이 어떻게 변하는지 확인한다.
3. SSE 연결 유지 중 DB 커넥션이 지속적으로 사용되는지 확인한다.
4. 목표 연결 수에 도달하지 못하는 최초 구간과 장애 원인을 확인한다.
5. 기존 폴링 방식과 비교해 반복 HTTP 요청과 DB 조회 비용이 얼마나 줄어드는지 확인한다.
6. 현재 단일 Spring Boot와 embedded Tomcat 구성에서의 SSE 연결 수용 한계를 확인한다.

기존 폴링 테스트를 다시 실행하지 않고 이미 측정한 결과를 비교 기준으로 사용한다.

---

## 2. 연결 유지 테스트만 진행하는 이유

기존 폴링 테스트에서는 테스트 도중 실제 알림을 계속 생성하지 않았다.

사용자별로 미읽음 알림을 사전에 저장한 뒤, 각 사용자가 5초마다 `unread-count` API를 호출하도록 구성했다. 사전에 저장한 알림은 실제 조회 대상 데이터를 준비하기 위한 것이며, 테스트 부하의 핵심은 반복적인 HTTP 요청과 DB 조회였다.

반면 현재 SSE 연결 테스트의 대상인 `/notifications/subscribe` API는 연결 과정에서 미읽음 알림을 조회하지 않는다.

SSE 구독 과정에서는 다음 동작만 수행한다.

1. 사용자 인증
2. `SseEmitter` 생성
3. 사용자와 Emitter 매핑
4. `connect` 이벤트 전송
5. 연결 유지

따라서 SSE 연결 유지 테스트에서는 알림 데이터를 별도로 생성할 필요가 없다.

테스트 도중 좋아요와 알림을 인위적으로 생성하면 다음 작업이 추가된다.

- 좋아요 데이터 저장
- 알림 데이터 저장
- DB 트랜잭션 처리
- 애플리케이션 이벤트 발행
- SSE notification 이벤트 전송

이 경우 SSE 연결 유지 비용뿐만 아니라 DB 쓰기와 이벤트 생성 비용까지 함께 측정된다. 기존 폴링 테스트에는 동일한 알림 생성 부하가 포함되지 않았으므로 두 방식의 서버 자원을 공정하게 비교하기 어려워진다.

따라서 이번 테스트에서는 대규모 알림 전달 테스트를 제외하고 다음 구조를 비교한다.

```text
폴링
사용자 증가 → 5초마다 HTTP 요청 → DB 조회 반복

SSE
사용자 증가 → 최초 연결 생성 → 장기 연결과 Emitter 유지
```

실제 `notification` 이벤트가 정상적으로 전달되는지는 소규모 기능 테스트로 확인할 수 있다. 수천 명을 대상으로 하는 알림 전달 처리량과 전달 지연 테스트는 이번 비교 범위에서 제외한다.

## 3. 테스트 범위와 한계

### 측정하는 항목

- SSE 연결 성공 여부
- 최대 활성 연결 수
- Steady State 연결 유지 상태
- 연결 실패 수
- CPU 평균과 최대 사용량
- JVM Heap 최대와 증가량
- JVM 라이브 스레드 수
- GC 횟수와 정지시간
- Hikari active/pending connection
- Tomcat busy threads
- 현재 서버 구성에서의 연결 한계

### 측정하지 않는 항목

- 실제 알림 전달 성공률
- 알림 누락과 중복
- 알림 전달 지연 p95·p99
- 초당 알림 처리량
- 알림 생성 과정의 DB 쓰기 성능
- 재연결 폭주 상황
- 다중 서버 환경의 이벤트 전달 성능

따라서 이번 결과로 SSE의 실제 알림 처리량이나 전달 지연시간을 판단하지 않는다. 결과는 SSE 연결 수용량과 연결 유지 비용을 분석하는 데만 사용한다.

## 4. 테스트 조건

모든 SSE 테스트는 기존 폴링 테스트와 동일한 로컬 환경에서 진행한다.

- Spring Boot, MySQL, k6를 동일한 로컬 머신에서 실행한다.
- 사용자별로 서로 다른 JWT를 사용한다.
- 테스트 중 로그인 요청은 발생시키지 않는다.
- k6 `SharedArray`로 JWT를 한 번만 읽는다.
- 각 VU에 고유한 JWT를 배정한다.
- 테스트 중 알림을 생성하지 않는다.
- 각 사용자는 SSE 연결을 한 번 생성한 뒤 유지한다.

부하 시간은 모든 테스트에서 다음 값으로 고정한다.

```text
Ramp-up: 60초
Steady State: 120초
Ramp-down: 30초
총 부하 실행시간: 210초
```

Actuator는 부하 테스트 시작 전에 수집을 시작하고 테스트 종료 이후까지 수집한다.

각 테스트 전에는 Spring Boot 서버를 재시작해 다음 상태를 초기화한다.

- SSE Emitter 저장소
- SSE 연결 누적 지표
- JVM Heap 상태
- GC 누적 지표
- Actuator 커스텀 지표

---

## 5. 테스트 방식

### 5.1 사용자 및 JWT 준비

DB에 미리 생성한 테스트 사용자 데이터를 사용한다.

Node.js 스크립트로 사용자별 JWT를 생성하고 하나의 JSON 파일에 배열 형태로 저장한다.

```text
VU 1 → loadtest1 사용자의 JWT
VU 2 → loadtest2 사용자의 JWT
...
VU 10000 → loadtest10000 사용자의 JWT
```

k6는 해당 JSON 파일을 `SharedArray`로 한 번만 불러오고 VU 번호에 맞는 JWT를 선택한다.

이를 통해 테스트 중 로그인 요청이 발생하지 않도록 하고, SSE 연결 부하만 측정한다.

### 5.2 SSE 연결 수립

각 VU는 자신의 JWT를 사용해 다음 API를 호출한다.

```text
GET /notifications/subscribe
```

연결 직후 서버에서 보내는 `connect` 이벤트를 수신하면 정상 연결로 판단한다.

확인 항목은 다음과 같다.

- SSE 연결 요청 성공 여부
- `connect` 이벤트 수신 여부
- 이벤트 이름 검증
- 서버의 활성 Emitter 수
- 연결 수립 실패 여부

### 5.3 연결 유지

Ramp-up 종료 후 목표 사용자 수의 SSE 연결을 Steady State 동안 유지한다.

Steady State에서는 별도의 폴링 요청이나 알림 생성 요청을 발생시키지 않는다.

이 구간에서 다음을 확인한다.

- 활성 Emitter가 목표 연결 수를 유지하는지 확인한다.
- 연결 수가 의도하지 않게 감소하는지 확인한다.
- CPU와 Heap이 안정적인 상태를 유지하는지 확인한다.
- 라이브 스레드가 지속적으로 증가하는지 확인한다.
- Hikari pending connection이 발생하는지 확인한다.
- Actuator가 계속 응답하는지 확인한다.

### 5.4 연결 종료

Ramp-down 과정에서 VU를 감소시킨다.

현재 사용하는 xk6 SSE 클라이언트는 장기 연결 iteration을 테스트 종료 시 중단할 수 있으므로, 테스트 종료 직후의 잔여 Emitter는 서버 메모리 누수로 바로 판단하지 않는다.

Emitter 정리 여부는 다음 항목을 함께 확인해 판단한다.

- 클라이언트가 연결을 정상 종료했는지 확인한다.
- 서버의 completion, timeout, error callback이 실행됐는지 확인한다.
- 서버 재시작 없이 Emitter가 감소하는지 확인한다.
- 단위 테스트에서 Emitter 제거 동작이 정상인지 확인한다.

## 6. 사용자 증가 단계

연결 한계점을 넓은 구간으로 탐색하기 위해 다음 순서로 진행한다.

| 단계 | 사용자 수 | 목적 |
| --- | ---: | --- |
| 스모크 | 10명 | 연결과 `connect` 이벤트 검증 |
| 기본 부하 | 500명 | 초기 서버 자원 기준값 측정 |
| 확장 | 2,000명 | 폴링 결과와 연결 유지 비용 비교 |
| 폴링 안정 구간 비교 | 5,000명 | 대규모 연결 안정성과 자원 증가 확인 |
| 연결 한계 탐색 | 10,000명 | Tomcat 및 JVM 연결 수용 한계 확인 |

모든 폴링 사용자 수를 동일하게 반복하지 않는다.

SSE는 폴링과 병목 구조가 다르기 때문에 다음처럼 넓게 사용자 수를 증가시킨다.

```text
10 → 500 → 2,000 → 5,000 → 10,000명
```

실패 구간이 확인되면 마지막 성공값과 실패값 사이를 추가로 세분화할 수 있다.

다만 이번 테스트에서는 5,000명까지 정상 유지됐고 10,000명에서 Tomcat 기본 연결 상한으로 추정되는 8,192개에 도달했으므로 추가 세분화는 필수로 진행하지 않는다.

## 7. 필수 측정 지표

### 7.1 연결 안정성

| 지표 | 의미 |
| --- | --- |
| 목표 사용자 수 | 테스트에서 생성하려는 SSE 연결 수 |
| 최대 활성 연결 수 | 서버가 실제로 유지한 최대 Emitter 수 |
| 연결 이벤트 성공 수 | `connect` 이벤트를 정상적으로 받은 수 |
| 목표 연결 도달률 | 목표 사용자 중 최대 연결에 도달한 비율 |
| 연결 시도 실패 수 | 연결을 수립하지 못한 요청 수 |
| Steady 활성 Emitter | Steady State 동안 유지된 실제 연결 수 |
| 비정상 종료 수 | 테스트 의도와 관계없이 종료된 연결 수 |
| 마지막 확인 Emitter | Actuator가 마지막으로 확인한 Emitter 수 |

목표 연결 도달률은 다음과 같이 계산한다.

```text
목표 연결 도달률
= 최대 활성 연결 수 / 목표 사용자 수 × 100
```

연결 실패 후 동일 VU가 재시도할 수 있으므로 전체 연결 시도 성공률과 목표 연결 도달률을 구분한다.

```text
연결 시도 성공률
= 성공 연결 시도 / 전체 연결 시도 × 100
```

연결 유지율은 Steady State 동안 정상적으로 수집된 Actuator 데이터를 기준으로 판단한다.

```text
연결 유지율
= Steady State 최소 활성 Emitter / 최대 활성 Emitter × 100
```

### 7.2 서버 자원

| 지표 | 확인 목적 |
| --- | --- |
| CPU Steady 평균 | 연결 유지 상태의 CPU 비용 |
| CPU 최대 | 연결 수립 과정의 순간 부하 |
| JVM Heap 최대 | 전체 연결 유지에 필요한 메모리 |
| JVM Heap 증가량 | 테스트 시작 대비 연결 유지 메모리 증가량 |
| JVM 라이브 스레드 최대 | 연결 수 증가에 따른 스레드 변화 |
| Hikari active 최대 | 연결 과정에서 발생한 DB 사용량 |
| Hikari pending 최대 | DB 커넥션 풀 병목 여부 |
| GC 횟수 | 연결 증가에 따른 GC 발생량 |
| GC 누적 pause | GC로 인해 중단된 총시간 |
| GC 최대 pause | 가장 긴 GC 정지시간 |
| Tomcat busy threads | 요청 처리 스레드 사용량 |
| Actuator 응답 여부 | 서버 상태 조회 가능 여부 |

SSE 연결 테스트에서는 Emitter와 장기 연결 때문에 Heap 사용량이 주요 지표가 된다.

GC와 Tomcat 지표는 연결 실패, 지연 또는 Actuator 장애가 발생했을 때 원인을 분석하는 핵심 보조 지표로 사용한다.

## 8. 테스트 통과 조건

다음 조건을 만족하면 해당 사용자 수를 안정적인 연결 유지 구간으로 판단한다.

```text
목표 연결 도달률 ≥ 99%
Steady State 연결 유지율 ≥ 99%
연결 시도 실패가 지속적으로 발생하지 않음
Steady State 중 활성 Emitter가 비정상적으로 감소하지 않음
Steady State 중 Heap이 지속적으로 증가하지 않음
Hikari pending connection이 지속적으로 발생하지 않음
Actuator가 테스트 전 구간에서 정상적으로 응답함
```

다음 상태가 반복되거나 지속되면 연결 한계에 도달한 것으로 판단한다.

- 최대 활성 연결 수가 목표치에 도달하지 못했다.
- 연결 수를 늘려도 실제 활성 Emitter가 더 이상 증가하지 않았다.
- 연결 요청이 장시간 대기한 뒤 실패했다.
- 연결 실패가 반복적으로 발생했다.
- Steady State 이전에 Actuator 수집이 중단됐다.
- Heap과 GC 부담이 급격하게 증가했다.
- 서버가 정상적으로 실행 중이지만 새로운 연결을 수용하지 못했다.

한 번의 CPU 또는 GC 이상치만으로 실패를 판단하지 않는다. 연결 수, 실패 수, Heap, GC 및 Actuator 응답 상태를 함께 확인한다.

## 9. 기존 폴링과 비교할 항목

기존 폴링을 다시 실행하지 않고 이미 측정한 결과를 비교 기준으로 사용한다.

### 직접 비교 가능한 항목

| 비교 항목 | 폴링 | SSE |
| --- | --- | --- |
| 사용자 수 | 동일 | 동일 |
| CPU 평균 | 5초 주기 요청 처리 비용 | 연결 유지 비용 |
| JVM Heap 최대 | 요청 처리 객체와 DB 조회 비용 | Emitter와 장기 연결 유지 비용 |
| 라이브 스레드 | 반복 요청 처리 스레드 | 비동기 연결 유지 스레드 |
| Hikari active/pending | 반복적인 unread-count DB 조회 | 연결 중 DB 사용 여부 |
| GC | 반복 요청 객체 생성 비용 | 다수 Emitter 유지 비용 |
| 안정적으로 수용한 사용자 수 | 목표 RPS 처리 가능 여부 | 목표 연결 유지 가능 여부 |
| 장애 지점 | 응답 지연과 처리량 저하 | 연결 수용 상한과 Heap 증가 |

기존 폴링 결과는 다음과 같다.

| 사용자 수 | 폴링 결과 |
| ---: | --- |
| 5,000명 | 약 1,000 RPS를 100% 성공 처리했다. |
| 6,250명 | p95가 약 524.79ms로 증가했다. |
| 7,500명 | p95가 약 1.58초까지 증가했다. |
| 10,000명 | 목표 처리량 미달과 실패가 발생했다. |

SSE에서는 동일 사용자 수가 만드는 반복 RPS가 없다. 최초 연결 요청 이후에는 장기 연결만 유지하기 때문이다.

따라서 폴링의 RPS와 SSE 연결 수를 같은 처리량 지표로 직접 비교하지 않는다. 동일 사용자 수에서 발생하는 CPU, Heap, 스레드, DB 커넥션 및 안정성을 비교한다.

### 직접 비교하지 않는 항목

기존 폴링 테스트에서는 실제 알림 생성과 전달 지연을 측정하지 않았다. 따라서 다음 항목은 비교하지 않는다.

- 알림 전달 성공률
- 알림 누락과 중복
- 알림 전달 지연 p95·p99
- 동일 이벤트 발생률에서의 서버 자원
- 초당 알림 처리량

폴링의 5초 주기에서는 새로운 알림 확인이 최대 약 5초 지연될 수 있다는 구조적인 차이만 설명한다.

```text
평균 이론 대기시간: 약 2.5초
p95 이론 대기시간: 약 4.75초
최대 이론 대기시간: 약 5초 + API 응답시간
```

해당 값은 실측 알림 전달 지연이 아니라 폴링 주기로 계산한 이론값임을 명시한다.

## 11. 테스트 결과의 해석 범위

이번 테스트에서는 SSE 연결 수용량과 연결 유지 비용만 측정한다.

따라서 다음 결론을 내릴 수 있다.

- 폴링 대비 반복 HTTP 요청과 DB 조회가 감소했는지 판단할 수 있다.
- 사용자 증가에 따른 SSE 연결 유지 비용을 확인할 수 있다.
- 현재 단일 서버에서 안정적으로 유지할 수 있는 연결 규모를 판단할 수 있다.
- 연결 실패가 발생하는 서버 계층을 추정할 수 있다.
- Heap과 GC가 SSE 확장의 주요 제약인지 판단할 수 있다.

반면 다음 결론은 내리지 않는다.

- SSE 알림이 대규모 환경에서 누락 없이 전달된다고 단정하지 않는다.
- 실제 알림 전달 지연시간을 단정하지 않는다.
- 초당 처리 가능한 알림 수를 단정하지 않는다.
- 다중 서버 환경에서도 동일한 결과가 나온다고 단정하지 않는다.

대규모 알림 전달량과 전달 지연이 실제 서비스 요구사항이 된다면 별도의 테스트 계획을 수립한다.

이번 테스트의 최종 목적은 SSE가 알림을 얼마나 빠르게 전달하는지가 아니라, **폴링의 반복 조회 비용을 제거했을 때 발생하는 연결 유지 비용과 현재 서버의 연결 수용 한계를 확인하는 것**이다.
