# 미읽음 알림 폴링 부하 테스트 보고서

## 1. 테스트 목적

알림 확인 지연을 줄이기 위해 폴링 주기를 단축했을 때 요청량과 Spring Boot 애플리케이션의 자원 사용량이 어떻게 변하는지 확인한다.

새로운 알림이 없어도 접속 사용자 수와 폴링 빈도에 비례해 요청이 발생하는 폴링의 구조적인 비용을 측정하고, 현재 로컬 환경에서 사용자 체감 지연과 처리 실패가 시작되는 구간을 찾는다.

## 2. 테스트 조건

- 대상 API: `GET /notifications/unread-count`
- 첫 요청: 사용자별로 폴링 주기 안에서 무작위 분산
- 후속 요청: 설정한 폴링 주기의 고정 tick
- Steady state: 120초
- 500 VU 이하: Ramp-up 30초, Ramp-down 30초
- 2,000 VU 이상: Ramp-up 60초, Ramp-down 30초
- k6, Spring Boot와 MySQL은 동일한 로컬 장비에서 실행
- Actuator 지표는 별도 스크립트로 5초마다 수집
- 성능 기준: 성공률 99% 이상, p95 500ms 미만, p99 1초 미만

2,000 VU 이상에서는 로그인 요청의 BCrypt 검증과 토큰 발급 비용이 측정에 섞이지 않도록 테스트 사용자별 JWT를 미리 생성했다. k6는 `SharedArray`로 토큰을 한 번만 읽고 각 VU에 서로 다른 사용자를 배정했다.

## 5. 결과 해석

### 폴링의 구조적인 비용

폴링 요청량은 다음 관계로 결정된다.

```text
예상 RPS = 동시 활성 사용자 수 / 폴링 주기
```

사용자를 500명으로 고정하고 폴링 주기를 30초에서 5초로 줄이자 Steady 요청 수와 RPS가 정확히 6배 증가했다.

```text
500명 × 30초: 2,000건, 16.67 RPS
500명 × 5초: 12,000건, 100 RPS
```

새로운 알림이 없어도 모든 활성 사용자가 같은 주기로 DB 조회를 반복한다. 알림 확인의 최대 지연을 30초에서 5초로 줄이기 위해 요청량과 서버 내부 작업을 6배 늘려야 하는 것이 폴링의 구조적인 비용이다.

### 안정 구간: 5,000명

5,000명이 5초마다 폴링하는 약 1,000 RPS까지는 성공률 100%와 안정적인 평균·p95 응답시간을 유지했다. 다만 p99가 217.71ms로 증가하고 Hikari pending과 요청 처리 스레드 증가가 나타나면서 순간적인 꼬리 지연의 초기 신호를 확인했다.

### 초기 체감 성능 임계점: 6,250명

6,250명에서는 목표한 약 1,250 RPS와 성공률 100%를 유지했고 p99도 1초 미만이었다. 하지만 p95가 524.79ms로 설정한 500ms 기준을 처음 초과했다.

Steady state 중 Hikari 커넥션 10개가 모두 사용되고 최대 189개의 대기 요청이 발생했다. 모든 요청이 느린 것은 아니지만 부하가 집중되는 순간 상위 5% 요청에서 사용자가 알림 반영 지연을 느낄 가능성이 나타난 경계 구간이다.

### 명확한 성능 저하: 7,500명

7,500명에서는 1,500 RPS와 성공률 100%를 유지했지만 p95가 1.58초, p99가 2.44초까지 증가했다. DB 커넥션 풀 포화와 요청 처리 스레드 점유가 Steady state 중 반복됐으며 사용자 체감 수준의 꼬리 지연이 명확해졌다.

### 처리 용량 및 가용성 한계: 10,000명

10,000명에서는 목표한 2,000 RPS를 만들지 못하고 실제 요청량이 약 1,165 RPS에 머물렀다. Steady state 성공률은 84.96%로 하락했고 평균 5.01초, p95 9.04초, p99 10.39초가 발생했다.

응답시간이 폴링 주기인 5초를 넘으면서 k6가 놓친 tick을 건너뛰었고 성공 처리량은 약 990 RPS에 머물렀다. Hikari 커넥션과 Tomcat 요청 처리 스레드가 포화돼 API뿐 아니라 Actuator 연결도 실패했으며 테스트 종료 시 Tomcat Acceptor의 소켓 옵션 오류도 발생했다.

CPU가 완전히 포화되기 전에 DB 커넥션과 요청 처리 스레드 대기가 먼저 병목이 됐다. 부하가 끝난 뒤에는 대기 커넥션이 빠르게 0으로 감소했으므로 서버 프로세스가 중단된 것이 아니라 처리 용량을 초과한 과부하 상태로 판단했다.

## 6. 사용자 체감과 임계점

6,250명은 전체 가입자 수가 아니라 5초마다 알림을 조회하는 동시 활성 사용자 수다. 따라서 현재 서버가 전체 사용자 6,250명밖에 수용하지 못한다는 의미는 아니다.

5초 폴링 자체의 확인 지연에 서버 응답시간이 더해지므로 6,250명 조건의 상위 요청에서는 새 알림 반영이 약 5.5~5.9초까지 늦어질 수 있다. 7,500명에서는 이 추가 지연이 1~2초 이상으로 증가해 알림이 바로 반영되지 않는다는 느낌이 더 명확해진다.

더 중요한 문제는 보조 기능인 알림 폴링이 DB 커넥션과 요청 처리 스레드를 점유한다는 점이다. 실제 서비스에서는 게시글, 댓글과 좋아요 같은 핵심 API도 같은 자원을 사용하므로 반복 폴링 비용이 서비스 전체 응답시간에 영향을 줄 수 있다.

현재 성능 기준을 적용한 결과는 다음과 같다.

| 구간 | 판정 |
|---:|---|
| 5,000명 · 약 1,000 RPS | 모든 기준을 만족한 안정 구간 |
| 6,250명 · 약 1,250 RPS | p95 기준을 처음 초과한 초기 체감 성능 임계점 |
| 7,500명 · 약 1,500 RPS | p95·p99가 크게 증가한 명확한 성능 저하 구간 |
| 10,000명 · 약 2,000 요구 RPS | 처리량 정체와 실패가 발생한 가용성 한계 |

정확한 한 명 단위의 임계점이 아니라 현재 로컬 환경에서 성능 저하가 시작되는 구간은 5,000~6,250명, 약 1,000~1,250 RPS 사이라고 결론 내렸다.

## 7. 테스트 후기와 기술 도입 필요성

낮은 사용자 수에서는 응답시간 저하가 없었지만, 사용자 증가와 폴링 주기 단축에 따라 알림 발생 여부와 무관한 요청, DB 조회, CPU 사용과 GC 작업이 선형적으로 증가했다. 서버가 완전히 중단되는 지점뿐 아니라 성공률은 유지하면서 사용자가 지연을 느끼기 시작하는 성능 임계점도 확인할 수 있었다.

서비스가 성장해 동시 활성 사용자 10,000명 이상을 수용해야 하는 상황을 목표로 한다면 현재 5초 폴링 방식은 충분한 여유를 제공하기 어렵다. 새로운 알림이 있을 때만 서버가 데이터를 전달하는 SSE를 도입해 불필요한 반복 요청을 줄일 필요성을 확인했다.

다음 단계에서는 SSE의 연결 유지, emitter 정리와 재연결 비용까지 포함해 같은 조건에서 폴링과 SSE의 요청량, 응답성, CPU, 메모리 사용을 비교한다. 이번 결과는 SSE가 항상 우월하다는 결론이 아니라 기술 도입의 가설과 비교 기준으로 사용한다.

## 8. 측정의 한계

- 로컬 단일 실행 결과이므로 운영 서버의 절대적인 최대 수용 인원을 의미하지 않는다.
- k6, Spring Boot와 MySQL이 같은 장비의 CPU, 메모리와 네트워크 자원을 공유했다.
- CPU, 응답시간과 GC는 캐시, JIT 컴파일과 OS 스케줄링의 영향을 받을 수 있다.
- 10,000명 과부하 구간에서는 Actuator도 응답하지 못해 내부 지표가 일부 누락됐다.
- 테스트마다 JVM 시작 상태가 완전히 같지 않았던 초기 결과가 있어 Heap 절대값 비교에는 주의가 필요하다. 임계점 확인을 위한 6,250명과 최종 7,500명 테스트는 JVM 재시작 후 측정했다.
- 미읽음 알림 API만 반복 호출했으므로 실제 서비스의 게시글, 댓글, 쓰기 요청이 섞인 트래픽과는 차이가 있다.
- 최대 응답시간은 소수의 이상치 영향을 크게 받으므로 평균, p95와 p99를 함께 해석했다.
