# 미읽음 알림 폴링 부하 테스트 보고서

## 1. 테스트 목적

알림 확인 지연을 줄이기 위해 폴링 주기를 단축했을 때 요청량과 Spring Boot 애플리케이션의 자원 사용량이 어떻게 변하는지 확인한다.

이 테스트의 목적은 폴링의 성능 저하를 의도적으로 발생시키는 것이 아니다. 새로운 알림이 없어도 접속 사용자 수와 폴링 빈도에 비례해 요청이 발생하는 폴링의 구조적인 비용을 정량적으로 확인한다.

## 2. 테스트 조건

- 대상 API: `GET /notifications/unread-count`
- Ramp-up: 30초
- Steady state: 120초
- Ramp-down: 30초
- 첫 요청: 사용자별로 폴링 주기 안에서 무작위 분산
- 후속 요청: 설정한 폴링 주기의 고정 tick
- k6와 Spring Boot는 동일한 로컬 환경에서 실행
- Actuator 지표는 별도 스크립트로 5초마다 수집

비밀번호는 결과 파일이나 스크립트에 저장하지 않고 `LOAD_TEST_PASSWORD` 환경변수로 전달했다.

## 3. 최종 비교 결과

응답시간과 성공률은 로그인 요청을 제외한 Steady state의 폴링 전용 지표다. 실제 RPS는 `Steady 요청 수 / 120초`로 계산했다.

| 동시 사용자 | 폴링 주기 | Steady 요청 수 | 실제 RPS | 성공률 | 평균 | p95 | p99 | Steady CPU 평균 | Heap 최대 | Hikari active 최대 | Hikari pending 최대 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 100명 | 30초 | 400 | 3.33 | 100% | 11.75ms | 18.70ms | 23.59ms | 약 0.32% | 약 110.2MiB | 1 | 0 |
| 500명 | 30초 | 2,000 | 16.67 | 100% | 9.40ms | 14.31ms | 18.48ms | 약 0.97% | 약 105.5MiB | 1 | 0 |
| 500명 | 5초 | 12,000 | 100 | 100% | 7.70ms | 12.75ms | 21.32ms | 약 4.06% | 약 105.2MiB | 3 | 0 |

## 4. k6와 Actuator 데이터 검증

각 테스트에서 k6의 전체 폴링 요청 수와 Actuator의 미읽음 API 누적 요청 수 증가량이 일치했다.

| 조건 | k6 전체 폴링 요청 | Actuator 요청 증가량 |
|---|---:|---:|
| 100명 × 30초 | 521 | 521 |
| 500명 × 30초 | 2,582 | 2,582 |
| 500명 × 5초 | 15,498 | 15,498 |

500명 × 5초 테스트의 전체 폴링 평균은 k6에서 약 7.35ms, Actuator에서 계산한 서버 내부 평균은 약 6.77ms였다. 약 0.58ms의 차이는 요청 전송과 응답 수신 등 애플리케이션 외부 구간으로 볼 수 있다.

## 5. 결과 해석

### 사용자 증가

폴링 주기를 30초로 고정하고 사용자를 100명에서 500명으로 늘리자 Steady 요청 수와 RPS가 정확히 5배 증가했다.

```text
100명 × 30초: 400건, 3.33 RPS
500명 × 30초: 2,000건, 16.67 RPS
```

### 폴링 주기 단축

사용자를 500명으로 고정하고 폴링 주기를 30초에서 5초로 줄이자 Steady 요청 수와 RPS가 정확히 6배 증가했다.

```text
500명 × 30초: 2,000건, 16.67 RPS
500명 × 5초: 12,000건, 100 RPS
```

이때 Steady CPU 평균은 약 0.97%에서 4.06%로 증가했고, GC와 활성 DB 커넥션도 함께 증가했다. Heap 최대 사용량은 비슷했으므로 요청 증가로 객체 할당 속도와 GC 빈도가 높아졌지만 메모리가 지속적으로 누적되지는 않은 것으로 판단했다.

평균과 p95 응답시간은 악화되지 않았고 요청 실패와 HikariCP 대기도 발생하지 않았다. 따라서 현재 로컬 환경에서 100 RPS는 성능 한계에 도달한 부하가 아니다.

### 폴링의 구조적인 비용

폴링 요청량은 다음 관계로 결정된다.

```text
예상 RPS = 동시 활성 사용자 수 / 폴링 주기
```

새로운 알림이 없어도 모든 활성 사용자가 같은 주기로 미읽음 개수를 조회한다. 알림 확인의 최대 지연을 30초에서 5초로 줄이기 위해 요청량과 서버 내부 작업을 약 6배 늘려야 한다는 점이 이번 테스트의 핵심 결과다.

## 6. 결론

500명 × 5초 폴링에서도 서버는 100 RPS를 안정적으로 처리했다. 따라서 이 결과만으로 폴링이 현재 서비스에서 사용할 수 없는 방식이라고 결론 내릴 수 없다.

다만 사용자 증가와 폴링 주기 단축에 따라 실제 알림 발생 여부와 무관한 요청, DB 조회, CPU 사용과 GC 작업이 함께 증가하는 구조를 확인했다. 이후에는 새로운 알림이 발생했을 때만 데이터를 전달하는 SSE를 구현하고, 반복 요청 비용과 연결 유지·재연결 관리 비용을 같은 조건에서 비교한다.

## 7. 측정의 한계

- 로컬 단일 실행 결과이므로 운영 EC2와 동일한 성능을 의미하지 않는다.
- k6와 Spring Boot가 같은 장비의 자원을 공유했다.
- CPU, 응답시간과 GC는 캐시, JIT 컴파일, OS 스케줄링의 영향을 받을 수 있다.
- 2,000명 이상의 값은 `사용자 수 / 폴링 주기`로 요청량만 계산할 수 있으며, CPU와 응답시간은 별도 실험 없이 선형 증가한다고 단정할 수 없다.
- 최대 응답시간은 소수의 이상치 영향을 크게 받으므로 평균, p95, p99와 함께 해석해야 한다.
