# SSE 연결 유지 부하 테스트

## 1. 테스트 목적

기존 5초 폴링 테스트에서는 새로운 알림의 발생 여부와 관계없이 사용자 수에 비례해 HTTP 요청과 DB 조회가 반복적으로 증가했다.

이번 테스트에서는 SSE가 폴링의 반복 조회 비용을 제거했을 때 발생하는 연결 유지 비용과 현재 단일 Spring Boot 서버의 연결 수용 한계를 확인했다.

대규모 알림 전달 테스트는 범위에서 제외했다. 기존 폴링 테스트에서도 테스트 도중 실제 알림을 생성하지 않았으므로, SSE 테스트에만 알림 생성과 DB 쓰기 부하를 추가하면 두 방식을 동일한 조건으로 비교하기 어렵기 때문이다.

따라서 다음 항목을 중심으로 측정했다.

- 최대 활성 SSE 연결 수
- 목표 연결 도달 여부와 연결 실패 수
- Steady State 연결 유지 상태
- CPU와 JVM Heap 사용량
- JVM 라이브 스레드와 GC
- Hikari active/pending connection
- 현재 Tomcat 구성에서의 연결 수용 한계

실제 알림 전달 성공률, 전달 지연 p95·p99, 초당 알림 처리량은 이번 결과에 포함하지 않았다.

---

## 2. 테스트 조건

- Spring Boot, MySQL, k6를 동일한 로컬 머신에서 실행했다.
- 사용자별로 서로 다른 사전 발급 JWT를 사용했다.
- k6 `SharedArray`로 JWT 파일을 한 번만 불러왔다.
- 테스트 중 로그인 요청과 알림 생성 요청은 발생시키지 않았다.
- 각 VU는 SSE 연결을 수립한 뒤 Steady State 동안 연결을 유지했다.

2,000명 이후 비교 테스트에서는 다음 시간을 고정 적용했다.

```text
Ramp-up: 60초
Steady State: 120초
Ramp-down: 30초
총 부하 실행시간: 210초
```

500명 테스트는 테스트 시간 고정 전에 수행한 초기 결과이므로 이후 결과와 시간 조건이 다르다.

## 5. 5,000명 폴링과 SSE 비교

| 지표 | 5초 폴링 | SSE 연결 유지 |
| --- | ---: | ---: |
| 사용자 수 | 5,000명 | 5,000명 |
| 반복 요청량 | 약 1,000 RPS | 반복 요청 없음 |
| 성공률 | 100% | 연결 성공률 100% |
| CPU 평균 | 약 9.21% | 약 0.08% |
| JVM Heap 최대 | 약 260.8MiB | 약 682.4MiB |
| 라이브 스레드 최대 | 약 216개 | 약 29개 |
| Hikari active 최대 | 10개 | 1개 |
| Hikari pending 최대 | 188개 | 0개 |

폴링은 사용자 수 증가에 따라 HTTP 요청과 DB 조회가 선형적으로 증가했다. 5,000명에서 약 1,000 RPS가 발생했고 Hikari active connection은 최대치인 10개까지 사용됐다. 대기 커넥션도 최대 188개 발생했다.

SSE는 최초 연결 이후 반복적인 `unread-count` 요청과 DB 조회가 발생하지 않았다. 5,000개의 연결을 유지하는 동안 CPU와 DB 커넥션 사용량은 낮게 유지됐다.

반면 SSE의 JVM Heap 최대 사용량은 폴링보다 높았다. SSE 서버가 사용자별 장기 소켓 연결과 `SseEmitter` 객체를 메모리에 유지하기 때문이다.

따라서 두 방식은 다음과 같은 비용 구조 차이를 보였다.

```text
폴링
→ 반복 HTTP 요청과 DB 조회
→ CPU, 스레드, DB 커넥션 비용 증가

SSE
→ 반복 요청과 DB 조회 제거
→ 장기 연결, Emitter, JVM Heap 비용 증가
```

폴링 API 응답시간과 SSE 연결 Handshake 시간은 서로 다른 작업이므로 직접 비교하지 않았다.

## 6. 10,000명 연결 실패 분석

10,000명 테스트에서는 k6가 10,000 VU까지 증가했지만 실제 `connect` 이벤트는 8,192건에서 멈췄다. 이후 연결 요청은 약 7.8초 동안 대기한 뒤 반복적으로 실패했다.

Actuator에서는 마지막으로 7,558개의 Emitter를 확인한 이후 정상적인 데이터 수집이 중단됐다. JVM Heap은 확인 가능한 구간에서 약 947.4MiB까지 증가했다.

Hikari pending connection은 0개였고 active connection도 최대 1개에 그쳤다. 서버 로그에서도 별도의 애플리케이션 예외는 발생하지 않았다. 따라서 DB 커넥션 풀이 직접적인 장애 원인은 아니라고 판단했다.

Spring Boot 프로세스의 파일 디스크립터 제한은 `1,048,576`으로 충분했다. 또한 `application.yaml`과 `application-local.yaml`에는 `server.tomcat.max-connections`가 별도로 설정되어 있지 않았다.

성공한 연결 수 8,192개가 embedded Tomcat NIO 커넥터의 기본 `maxConnections` 값과 일치했으므로, 현재 구성에서 Tomcat connector의 동시 연결 상한에 도달한 것으로 판단했다.

이는 SSE 프로토콜 자체의 연결 한계가 아니라 현재 단일 Spring Boot 인스턴스와 embedded Tomcat 기본 설정에서 확인된 연결 수용 한계다.

## 7. 테스트 후기 및 결론

기존 폴링 테스트에서는 새로운 알림이 없어도 사용자가 5초마다 미읽음 알림 개수를 조회했다. 사용자 수가 증가할수록 HTTP 요청, DB 조회, 커넥션 풀 사용량과 요청 처리 스레드가 함께 증가했다.

SSE로 변경한 뒤에는 최초 연결 이후 새로운 알림이 없는 동안 별도의 HTTP 요청이나 DB 조회가 발생하지 않았다. 따라서 알림처럼 실제 이벤트 발생 빈도보다 조회 빈도가 높은 기능에서는, 새로운 이벤트가 있을 때만 서버가 데이터를 전달하는 SSE 방식이 구조적으로 더 적합하다고 판단했다.

하지만 SSE가 모든 자원 측면에서 무조건 저렴한 방식은 아니었다. 각 사용자의 연결을 장시간 유지해야 하므로 서버가 사용자별 소켓과 Emitter를 계속 관리해야 했다. 사용자 수가 증가할수록 JVM Heap 사용량과 GC 부담도 함께 증가했다.

즉, SSE는 서버 비용을 없앤 것이 아니라 비용의 형태를 변경했다. 폴링에서 발생하던 CPU, DB 커넥션, 요청 처리 스레드 비용을 줄이는 대신 장기 연결, Emitter와 JVM Heap 비용이 새롭게 발생했다.

이번 테스트에서는 5,000명까지 모든 연결을 안정적으로 유지했다. 10,000명에서는 Tomcat 기본 연결 상한인 8,192개에 도달해 목표 연결을 모두 수립하지 못했다. 이를 통해 `maxConnections`와 같은 서버 설정이 SSE의 실제 연결 수용량을 결정하는 중요한 조건이라는 점도 확인했다.

더 많은 사용자를 수용하려면 Tomcat `maxConnections`와 JVM Heap을 함께 조정하고 다시 검증해야 한다. 단일 JVM의 메모리 부담이 커진다면 여러 서버로 SSE 연결을 분산하고 Redis Pub/Sub이나 Kafka를 통해 알림 이벤트를 전달하는 구조도 검토해야 한다.

결론적으로 SSE는 폴링의 불필요한 반복 요청과 DB 조회를 제거했지만, 장기 연결과 메모리 용량을 고려한 서버 설계가 필요한 방식이었다.

이번 결과는 k6, Spring Boot와 MySQL을 동일한 로컬 머신에서 실행한 결과다. 실제 알림 전달 처리량과 전달 지연시간은 측정하지 않았으므로 운영 환경의 절대적인 최대 수용 인원이나 대규모 알림 전달 성능으로 일반화하지 않는다.

이번 테스트는 폴링과 SSE의 비용 구조가 어떻게 달라지는지, 그리고 SSE를 대규모로 확장할 때 어떤 자원이 새로운 병목이 되는지를 확인한 비교 자료로 활용한다.

## 8. 향후 확장 방안

1. 예상 동시 접속자와 여유 용량을 기준으로 Tomcat `maxConnections`를 명시적으로 조정한다.
2. 연결 상한을 조정한 뒤 JVM Heap과 GC를 포함해 10,000명 연결을 다시 검증한다.
3. 단일 JVM의 메모리 부담이 크다면 Load Balancer를 이용해 SSE 연결을 여러 서버로 분산한다.
4. 다중 서버 환경에서는 Redis Pub/Sub이나 Kafka를 이용해 알림 이벤트를 각 SSE 서버로 전달한다.
5. 운영 환경의 Nginx buffering, idle timeout, 파일 디스크립터와 JVM Heap 설정을 함께 점검한다.
